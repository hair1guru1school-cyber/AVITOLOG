# СУПЕР ПОДРОБНОЕ ТЗ ДЛЯ COMPOSER

## 0) Роль и режим работы
Ты — Composer в режиме **архитектор + рефакторинг-оркестратор**.
Требуется не просто «переписать код», а подготовить поэтапный план с контролем риска, чтобы любой шаг можно было быстро откатить.

Цель: превратить текущий AVITOLOG-монолит в масштабируемый проект с пакетной структурой, документацией и обновляемым деплоем.

---

## 1) Бизнес-цель
- Упростить поддержку и развитие.
- Снизить риск поломок при добавлении новых функций.
- Повысить скорость выпуска обновлений.
- Подготовить проект к командной разработке.

---

## 2) Что нужно сделать обязательно
1. Выполнить декомпозицию на **5–8 основных пакетов**.
2. Разделить UI/бизнес-логику/интеграции/хранилище.
3. Убрать критичную связанность через глобальные переменные.
4. Добавить документацию архитектуры и runbook обновления.
5. Подготовить структуру для стабильного локального и веб-запуска.

---

## 3) Пакетная структура (рекомендуемая)

- `packages/core` — ядро приложения и жизненный цикл
- `packages/ui` — визуальные компоненты и рендер
- `packages/crm` — CRM домен
- `packages/goals` — домен целей/статусов/продаж
- `packages/integrations` — внешние API и клиенты
- `packages/storage` — слой хранения данных + миграции
- `packages/shared` — общие типы/утилиты/константы
- `packages/styles` — дизайн-система, темы, токены

Если 8 пакетов слишком много — допустимо 6, но нужно сохранить границы ответственности.

---

## 4) Детальная постановка по фазам

### Фаза A: Discovery
- Прочитать кодовую базу
- Найти все точки входа
- Составить матрицу «функция → модуль»
- Зафиксировать технический долг

Выход:
- `docs/discovery-report.md`
- `docs/module-boundaries.md`

### Фаза B: Target Architecture
- Описать целевую архитектуру
- Определить публичные API модулей
- Зафиксировать правила импорта

Выход:
- `docs/architecture-target.md`
- `docs/contracts.md`

### Фаза C: Incremental Migration
- Переносить по одному домену
- После каждого шага запускать smoke
- Делать маленькие коммиты

Выход:
- changelog по шагам
- migration logs

### Фаза D: Hardening
- Нормализовать обработку ошибок
- Централизовать уведомления
- Добавить guard checks

Выход:
- `docs/hardening-checklist.md`

### Фаза E: Release Readiness
- Сформировать release-plan
- Добавить rollback-инструкцию
- Описать процесс обновления

Выход:
- `docs/release-plan.md`
- `docs/rollback-playbook.md`

---

## 5) Нефункциональные требования
- Производительность: не ухудшить TTI
- Надёжность: устойчивость к отсутствию токена/сети
- Безопасность: исключить хранение чувствительных данных в открытом виде
- Поддерживаемость: читаемые модули и короткие файлы

---

## 6) Контроль качества
Composer обязан создать:
1. Smoke checklist
2. Риск-реестр
3. Таблицу регрессий
4. Таблицу «было/стало» по структуре
5. Набор команд для локальной проверки

---

## 7) Ожидаемый формат ответа Composer
Каждый ответ должен включать:
- Резюме фазы
- Изменённые файлы
- Риски
- Как проверить
- Следующий шаг

---

## 8) Финальный критерий приёмки
- Проект разбит на 5–8 пакетов
- Документация лежит в `docs/`
- Обновление проекта воспроизводимо
- Есть чёткий rollback
- Ключевые сценарии проходят smoke

---

## 9) Стартовая инструкция для Composer
Начни с Discovery и выдай:
1) карту модулей,
2) план миграции на 4–8 шагов,
3) список рисков с mitigations,
4) точный порядок безопасного переноса кода.
